## Highlights

- The AWS, Google Cloud and Azure deployments are more reliable on a first deploy and on later ones. AWS no longer returns intermittent 502 errors, redeploying the Azure template no longer signs everyone out, and the Google Cloud Terraform stops before it creates anything when a secret is missing. ([Deploy to AWS, Google Cloud or Azure](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md), [#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12))
- Password sign-in limits are harder to get around. A client with many IPv6 addresses is now limited as one client, and a client IP header can no longer be supplied by visitors on Google Cloud or Azure deployments that follow the guide. ([#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12))
- Scheduled jobs now fail clearly when `APP_URL` redirects, instead of reporting success without running. ([#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12))

## Upgrading from v0.6.0

This release is a patch version. Deployments that allow `~0.6.0` or `^0.6.0` receive it. It adds no required settings and no database changes, so `npm run db:migrate` is not required.

1. Fetch the `v0.6.1` tag and merge it into a new branch, keeping the local Dives, `dives.config.mjs` entries and branding. The steps are in [AGENTS.md](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/AGENTS.md#upgrade-a-copy-to-a-newer-release).
2. Run `npm ci`, `npm test` and `npm run build`.
3. Deployments on AWS, Google Cloud or Azure that pin the image to `0.6.0` change the tag to `0.6.1` and update the stack, service or template as described in each cloud's **Upgrade** section. Deployments that use `latest` receive the new image on their next restart or new revision.
4. Review the [Compatibility](#compatibility) section, in particular before deploying the Azure template again.

## Bug Fixes

- AWS ([AWS](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md#aws), [#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12)):
  - Requests occasionally failed with a 502 error because the app closed idle connections after 5 seconds while the load balancer kept them for 300 seconds. The app now keeps connections open longer than the load balancer.
  - A stack created in the console could fail when an account's first two Availability Zones included one without CloudFront VPC origin support, with no way to choose others. The template now has optional **AvailabilityZone1** and **AvailabilityZone2** parameters, and the guide lists the unsupported zones.
  - A daily run longer than 120 seconds was cut off, and could be repeated, by CloudFront's origin timeout. The scheduled jobs now call the internal load balancer directly.
  - `cdk synth` produced no stack on Node.js 24.0 and 24.1. The AWS tooling now requires Node.js 24.2 or later, and the guide says so.
- Google Cloud ([Google Cloud](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md#google-cloud), [#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12)):
  - Terraform enabled APIs and created service accounts before it reported a missing secret. It now stops before it creates anything.
  - A first apply with a custom domain could fail while the Compute Engine API was still being enabled. The load balancer resources now wait for it.
  - With a custom domain, sources inside the same project could reach the default `run.app` address and send their own client IP header. That address is now turned off when a domain is set.
  - The **Run on Google Cloud** button required the fields that the guide described as optional, did not apply the instance limit, and could fail on permissions granted right after a service account was created. The fields now have defaults, the limit is applied, and permission changes are retried.
  - A secret left without a value by an interrupted setup was kept as it was, which stopped the service from starting. The setup script now adds the value.
  - Long service names produced invalid or identical service account IDs. Both IDs are now valid and distinct, and the default name keeps its existing IDs.
- Azure ([Azure](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md#azure), [#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12)):
  - Each deployment of the template stored a new `SESSION_SECRET`, which signed everyone out. The new **Keep Generated Secrets** parameter keeps the stored values on later deployments.
  - The documented `az deployment group create` command never asked for the chat token or the model provider key, so chat stayed off. The guide now uses a Bicep parameters file that reads each secret from an environment variable.
  - Adding `APP_URL` for a custom domain created two `APP_URL` settings and failed the deployment. `APP_URL` is now set once, from **Settings** when present.
  - Secret names repeated in **Extra Secrets** or **Settings**, and empty optional values, failed the deployment or overrode other settings. Repeated names are now merged and empty values are ignored.
  - The scheduled job timeout could end a retry early. It now allows a full retry.
- Container and scheduled jobs ([#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12)):
  - `deploy/cron.mjs` followed redirects, so a job could report success after landing on another page, and could send the bearer token to another host. A redirect is now a failure with a message that names `APP_URL`.
  - Nested `node_modules`, `.next` and `.env` files were sent to the Docker build. They are now excluded.
- Interface ([#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12)):
  - Numbered lists in chat answers cut off the first digit of items 10 and above. They now have room for two digits.
  - **Activity** still showed `[object Object]` for lists of objects in some change details. Nested lists and objects are now listed in full.
- Shared password sign-in counted failures per IPv6 address, so a client with an IPv6 /64 could rotate addresses to avoid the limit. Failures now count per /64, as they already did for accounts, and IPv4-mapped addresses count as their IPv4 address. ([#12](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/pull/12))

## Compatibility

- On Azure, `trustedIpHeader` is safe only behind a proxy that overwrites the header, with `allowedIpRanges` admitting only that proxy and `APP_URL` set to the proxy's address. Deployments that set `trustedIpHeader` without such a proxy let visitors choose the address that failed sign-ins count against. Clear `trustedIpHeader` and use accounts, or add the proxy and `allowedIpRanges`. ([Password sign-in on Azure](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md#password-sign-in-on-azure))
- Azure deployments made with v0.6.0 set **Keep Generated Secrets** to `true` on every later deployment, so that sessions continue. ([Deploy again on Azure](https://github.com/leonardovida/motherduck-dive-ai-chat-starter/blob/v0.6.1/docs/deploy.md#deploy-again-on-azure))
- The Google Cloud Terraform turns off the default `run.app` address when a custom domain is set. Clients that used that address directly switch to the domain.
- Scheduled jobs whose `APP_URL` redirects now fail. Set `APP_URL` to the address the app answers on directly.
